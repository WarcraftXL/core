# How wxl-core works

## What the core is

`WarcraftXL.dll` runs inside the 3.3.5a client (build 12340, a 32-bit process). It is a neutral
runtime: it changes nothing in how the client behaves. It does three things:

- **raises events** at the client's own seams (a frame, a world change, a window message, a file open);
- **publishes services**, C tables an extension asks for by name (`wxl.storage`, `wxl.objects`,
  `wxl.settings`, `wxl.profiles`, `wxl.lua`, `wxl.graphics.device`, `wxl.net`);
- **loads extensions**, one DLL per folder under `Extensions\`, and isolates their faults.

Everything that changes the game is an extension. Extensions are built against the SDK (`wxl-sdk`):
its C ABI (`wxl/abi/Plugin.h`), the event table, the offsets and the C++ layer (the `Extension`
class, handlers, signals, interceptors). The core builds against the same SDK and implements its side.

`wxl-patcher.exe` makes the client load the DLL: it adds the `WarcraftXL.dll` import and the
large-address flag to `Wow.exe`, and nothing else.

## Boot

1. `DllMain` (`src/runtime/Main.cpp`) opens `Logs\wxl-core.log`, starts MinHook, and calls
   `extensions::InstallLoader()`: it publishes the core's services and attaches the two seams that
   will load the extensions. Nothing is loaded yet: `LoadLibrary` is not allowed under the loader lock.
2. The **Boot** features run (the Lua service, the device seam), then the hook batch is enabled.
3. A thread of the core installs the storage detours, waits for the graphics device, runs the
   **Normal** features (the other seams of `src/client/`), and enables the batch again.

A feature is a function registered with `WXL_REGISTER_FEATURE(name, enabled, Install)`
(`src/engine/hook/Registry.hpp`); `Install` attaches its detours.

## The path of an event

Take `OnUpdate`, raised once per frame:

1. **Seam.** `src/client/CWorldScene/World.cpp` attaches `FrameTimeDetour` to the hook point
   `"FrameTime::Update"`. The detour calls the client's function, then
   `events::Emit<Event::OnUpdate>(UpdateArgs{ dt, timeMs })`.
2. **Hook.** `hookpoints::Attach` finds the address in `HookPoints.def` and calls `hook::Install`.
   Every party on one address forms a chain (`src/engine/hook/Hook.cpp`); MinHook jumps to a small
   thunk, `jmp [head]`, so links can be added or removed while the game runs.
3. **Bus.** `Emit` walks the event's connections (`src/engine/events/Event.cpp`) in priority order,
   then connection order. A connection made during a walk is called from the next emit; one ended
   during a walk is skipped and released after it. Connections about one object (a subject) are kept
   apart: a plain emit never walks them, `EmitFor(event, subject, args)` merges them in.
4. **Owner guard.** A core handler is called directly. An extension's handler runs through
   `owners::Run` (`src/runtime/Owners.cpp`): the thread's current owner is set, and a hardware fault or
   an escaping exception is caught there.
5. **Extension.** The handler is the SDK's: an `On<Tag>` handler, a `wxl::Signal` connection, or the
   virtual an `Extension` overrides (connected only when overridden), which receives the typed args.

Some events carry an answer (`OnInput` has `handled`). Each extension handler sees the answer the
previous ones left; a handler that faults has its half-written answer put back.

## The life of an object handle

`wxl.objects` hands out a handle `{index, generation}` per resident object
(`src/runtime/objects/Objects.cpp`). The object manager's own lifetime points keep it exact
(`src/client/CGObject_C/Lifetime.cpp`): after `InitObject` built an object, and when `GetUpdateObject`
brings one back from the lazy-cleanup list, the handle is made and `OnObjectAdded` raised; before
`ObjDelete` (out of view, destroyed) and `DestroyRemovedObject` (the world torn down), `OnObjectRemoved`
is raised while the handle still resolves, then it expires and the connections about it end. Each
access also checks that the object manager still answers the same pointer for the GUID.

## The path of a hook and of an interceptor

- **Raw hook** (`wxl::Hook<Fn>` in the SDK). `WXL_Api::HookAttach` or `HookAttachByName`
  (`src/runtime/extensions/Api.cpp`) checks that the extension holds `permissions.low_level`, then
  adds a link to the address's chain. Raw detours run unguarded: they are the extension's own code on
  the client's stack. When the extension is disabled, `hook::DropOwner` takes its links out.
- **Interceptor** (`wxl::Intercept<Fn, Address>()` in the SDK). The extension's detour is a thunk of
  the function's exact convention, attached by `WXL_Api::InterceptAttach` (no permission needed). For
  each call it runs the Before, Replace and After handlers, each one through `WXL_Api::Run`, which is
  `owners::Call` under the guard. A handler that faults has its changes to the arguments and the
  result undone, and the call goes on.

## The path of a service

- **Publish.** `extensions::PublishInterface(name, version, table)` (`src/runtime/extensions/Services.cpp`)
  records it under the code running now: the core for its own services, an extension when it calls
  `WXL_Api::PublishInterface`.
- **Get.** `WXL_Api::GetInterface(name, version)` answers the highest published version at or above
  the one asked for. A table starts with `structSize`; members are only appended, so an older caller
  still works.
- **Take-back.** When an extension is disabled, its services are withdrawn: no one gets them any
  more, and those who hold the pointer keep it.

The core's services: `wxl.storage` (`src/engine/storage/StorageService.cpp`), `wxl.objects`
(`src/runtime/objects/ObjectsService.cpp`), `wxl.settings` (`src/runtime/settings/SettingsService.cpp`),
`wxl.profiles` (`src/engine/script/Profiles.cpp`), `wxl.lua` (`src/engine/script/LuaApi.cpp`),
`wxl.graphics.device` (`src/client/CGxDevice/DeviceCreate.cpp`), `wxl.net` (`src/runtime/net/NetService.cpp`).

## How an extension is loaded

1. **Folder.** `Extensions\<folder>\<folder>.dll` with its `wxl.json`, in folder-name order.
2. **Manifest** (`Manifest.cpp`, read before the DLL): `extension.abi` (the SDK version it was built
   for: same major, minor no greater than the core's), `extension.load` (`"engine"`, the default, or
   `"before-archives"`), `permissions.low_level`.
3. **Stage.** `before-archives` extensions load when the client starts mounting its archives
   (`OpenArchives`); the others at engine initialisation, or earlier when the client builds its
   graphics device (`EnsureLoaded`). `OnExtensionsLoaded` follows.
4. **Checks** (`Loader.cpp`): the exports `WXL_Query` and `WXL_Load`, the API version, the client
   build, the SDK version. A refusal is logged with its reason and leaves nothing loaded.
5. **Load.** The extension becomes an owner (`owners::Add`), then `WXL_Load(&api)` runs under the
   guard. Returning 0, or faulting, disables it.

## Fault isolation

An extension's code is called under `WXL_SEH_TRY` (the SDK's `wxl/Common.hpp`): its event handlers,
`WXL_Load`, releases, interceptor handlers and `wxl::Guarded` blocks. On a fault the extension is
**disabled** (`owners::Disable`): its code is never called again, and what it held is taken back:
its bus connections, its hook links, its patches (restored newest first) and its services. The log
says what happened and where (`extensions: '<name>' is disabled: ...`). The DLL stays loaded: one of
its detours may still be on a stack.

Not guarded: raw detours, Lua C functions, storage callbacks, the device factory, an extension's own
threads.

## How to add an event source

A new event is a new seam: a detour on a client function that raises a new row of the event table.

1. **Hook point.** The function must be in the SDK's offsets (`wxl/offsets/...`, generated from the
   atlas), with its `...Fn` signature alias. Add its name to the SDK's `tools/offsets/hookpoints.lua`
   and regenerate: `luajit tools/offsets/gen.lua --atlas <atlas> --core <wxl-core>` writes the SDK's
   `include/wxl/HookPoints.def` and this repository's `src/runtime/HookPoints.def`.
2. **Event row.** The event table lives in the **SDK**: append a row to
   `include/wxl/events/Events.def`, `WXL_EVENT(OnSomething, <next id>, SomethingArgs)`, and its args
   struct to `include/wxl/events/<Concept>Args.hpp`, and a line to the SDK's `docs/events.md`. Ids are
   the ABI: append only, never renumber; the SDK's `abi-lock` test holds them.
3. **Seam.** In `src/client/<Class>/<File>.cpp`:

   ```cpp
   off::Something::DoFn g_origDo = nullptr;

   int __cdecl DoDetour(void* thing)
   {
       const int result = g_origDo(thing);
       const ev::SomethingArgs args{ thing };
       ev::Emit<ev::Event::OnSomething>(args);
       return result;
   }

   bool InstallSomething()
   {
       return wxl::runtime::hookpoints::Attach("Something::Do", &DoDetour, &g_origDo);
   }

   WXL_REGISTER_FEATURE("something", true, InstallSomething)
   ```

   The detour has the function's exact calling convention (a `thiscall` is `__fastcall` with an unused
   `edx`). Raise the event before the call when handlers should see or change the input, after it when
   they should see the result. An event about one object is raised with `ev::EmitFor(event, handle,
   &args)`, so connections about that object hear it. A function the atlas marks `regparm` takes its
   arguments in registers: its detour is a naked thunk that keeps every register
   (`src/client/CGObject_C/LifetimeThunks.cpp`).
4. **Override and tag.** Add its row to the SDK's `include/wxl/Overrides.def`: the tag `On<Something>`
   takes, and the `OnSomething` virtual of `Extension` with the args unpacked. The SDK refuses to
   compile while the two tables differ in length.
5. **Test.** `ctest` checks the hook-point table against the SDK (`hookpoints-generated`). Add the
   seam to the `seams` test (`tests/seams/`): it links the seam files over fake hook points and a fake
   object manager, calls each detour with a fake original and checks what the bus received. Running
   the seam on the client itself is checked in the game.

## Checks

`ctest` (under wine from Linux): `loader`, `guard`, `objects`, `bus`, `patch`, `settings`, `storage`,
`seams`, `bench`, and `hookpoints-generated` when built with an SDK working copy. `bench` prints the
cost of one dispatch through the bus, a hook chain, an interceptor, an `On` handler, a signal, an
`Extension` override, an extension's log line and a walk of the settings, and fails if any of them
allocates per call. The core's floats are SSE2 (the SDK's targets
carry `/arch:SSE2`).
